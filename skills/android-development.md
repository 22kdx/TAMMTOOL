# دليل ممارسة الوكيل: تطوير تطبيقات Android وتشخيص بنائها

هذا دليل عمل قابل للمراجعة وإعادة الاستخدام داخل المستودع، وليس تدريبًا دائمًا للنموذج أو إثباتًا لاكتساب خبرة عملية غير مختبرة. تُراجع الإصدارات والأوامر وفق المشروع الفعلي قبل استخدامها. لا يغيّر توزيع مهام الوكلاء أو تعليمات المنسق.

## 1. فهم المشروع قبل التعديل
- اقرأ ملفي التواصل والحالة، وافحص الفرع وgit status قبل العمل.
- حدّد وحدات التطبيق، applicationId، SDK، JDK، AGP، Kotlin، Gradle وCompose compiler من الملفات، لا من الذاكرة.
- ميّز بين الفرع الذي تفحصه والفرع الذي تعمل عليه. قراءة git show لفرع آخر لا تعني أن مصادره موجودة محليًا.
- سجّل حدود المهمة وخطة تحقق صغيرة، ولا تستبدل ميزات سكريبت قائم دون مقارنة واجهته.

## 2. تشخيص البناء تدريجيًا
| المرحلة | الأدلة المطلوبة | أمثلة عوائق |
|---|---|---|
| البيئة | java -version، SDK، Wrapper | JDK مفقود، تنزيل محجوب |
| تهيئة Gradle | أول خطأ من tasks/assembleDebug | مستودعات متعارضة، plugin مفقود |
| Kotlin/Java | اسم المهمة الفاشلة ورسالة المترجم | imports، أهداف JVM، توافق Compose |
| توليد الكود | خرج kapt/KSP | bindings مفقودة، DAO غير صالح |
| الموارد والتغليف | خرج mergeResources/package | manifest، موارد متعارضة |
| التوقيع | تحقق apksigner | مفتاح أو كلمة مرور غير صالحة |
| الجهاز | adb devices وحالة التثبيت | unauthorized، تعدد الأجهزة |

ابدأ بأول خطأ أصلي لا بآخر رسالة عامة. لا تعالج فشل التهيئة بمسح cache عشوائيًا. لا تعتبر dry-run اختبار تجميع.

## 3. مراجعة Kotlin وHilt وRoom وCompose
- Kotlin: راجع nullability وأنواع Flow/StateFlow، نطاق coroutines والإلغاء، واستيرادات الامتدادات. لا تحول العمليات الثقيلة إلى Main thread.
- Hilt: تحقق من Application وAndroidEntryPoint وHiltViewModel وInject، وربط Application في Manifest، وتوافر bindings ومعالج annotations. لا تفترض غياب مشكلة لأن annotations موجودة.
- Room: تحقق من Entity وPrimaryKey، مطابقة أعمدة ونتائج SQL وأنواع DAO، نسخة database وmigrations. لا تستخدم destructive migration لإخفاء خطأ دون تفويض لأنها قد تمحو بيانات المستخدم.
- Compose: تحقق من زوج Kotlin/compiler وفق المرجع الرسمي، جمع الحالة بما يناسب lifecycle، مفاتيح القوائم، وعدم تنفيذ side effects مباشرة خلال composition. اختبر إعادة التكوين وحالات التحميل والخطأ والبيانات الفارغة.
- لا تستنتج صلاحية التطبيق كله من فحص Gradle فقط؛ انتقل لاختبارات الوحدة ثم الجهاز.

## 4. اختبار الأدوات وCI
```bash
python3 -m unittest discover -s scripts/tests -v
for file in scripts/*.sh; do bash -n "$file" || exit; done
bash scripts/diagnose-apk.sh marketer
```
الأمران الأولان لا يتطلبان مصادر Android؛ الثالث يتطلب مصادر التطبيق وبيئة البناء. لا تشغّل تثبيت SDK أو قبول رخصه دون التفويض المناسب.

- استخدم set -euo pipefail حيث يناسب، واحفظ PIPESTATUS فور pipeline إذا احتجت رمز Gradle الفعلي.
- اختبر النجاح والفشل وغياب APK والتعدد وعدم اعتماد الجهاز والمسارات ذات المسافات.
- ارفع السجل بـ if: always()؛ أعد رمز البناء الحقيقي بدل إخفائه بـ continue-on-error.
- ملف نصي placeholder ليس APK؛ فحص ZIP وحده لا يثبت صلاحية الحزمة. تحقق من metadata والتوقيع ثم التثبيت.
- عند حجب logs، جرّب run/jobs/check annotations عبر gh؛ نجاح metadata لا يعني نجاح تنزيل artifacts أو logs.

## 5. الأمن والجودة في تطبيقات الطلبات
- لا تطبع أسرار التوقيع أو مفاتيح API أو بيانات العملاء؛ راجع السجلات قبل نشرها.
- لا تضع keystore أو local.properties أو build outputs في Git.
- اختبر حالات انقطاع الشبكة، إعادة المحاولة، الطلبات المكررة والتحقق من المدخلات، مع مراعاة RTL واللغة العربية وإمكانية الوصول.
- نقل مستخدم الشاشة إلى التطبيق لا يثبت صحة تدفق الطلب أو وصوله للخادم. صمّم اختبارًا مستقلًا لسلوك المنتج.
- التثبيت عبر adb install -r يحافظ عادةً على البيانات؛ لا تحذف تطبيقًا آخر أو بياناته ضمن smoke test.

## 6. صيغة التسليم والتعلم من الأخطاء
كل تسليم يذكر: السبب المدعوم بدليل، الملفات المعدلة، الاختبارات ونتائجها، ما لم يُختبر، أثر التوافق، ومرجع commit/فرع التسليم. ميّز بدقة بين «محلي»، «مدفوع»، «مُدمج»، و«تم التحقق على جهاز».

بعد أي فشل، أضف اختبار regression عندما يمكن إعادة إنتاجه. أمثلة المشروع الحالية: فشل Gradle المخفي، نجاح دون APK، اختيار الجهاز، وتوقيع release بأدوات وهمية. الاختبار الوهمي يثبت منطق السكريبت لا صلاحية APK أو نجاح التوقيع الحقيقي.
